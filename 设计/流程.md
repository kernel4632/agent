# 后端流程

本文描述服务端指令如何修改数据。路由参数和响应格式以 [接口.md](接口.md) 为准，字段结构以 [数据.md](数据.md) 为准。

## 架构主线

所有业务请求遵循同一条链：

```text
HTTP 或 SSE 触发
  → server.js 中的路由识别动作并调用 command
  → command 读取、处理并修改 store
  → session watcher 发布 SSE，route 返回 HTTP 响应
```

`server.js` 中的路由不计算业务数据，只识别触发动作、提取参数并调用指令。指令修改数据后显式调用 SessionWatcher 反馈变化，但不分配事件 ID、操作事件缓冲、编码或发送 SSE 帧。store 不加载文件，也不执行方法。

## 启动与退出

### 启动

`server.js` 依次调用：

1. `Config.load()` 读取 `.agent/config.json`，文件不存在时创建默认配置。
2. `Workspace.load()` 读取 `.agent/workspace.json`，文件不存在时创建空列表。
3. 在 `server.js` 当前文件中注册四组 Elysia 路由。
4. 监听 `4632` 端口。

### 退出

收到 `SIGINT` 或 `SIGTERM` 后：

1. 对每个已加载会话调用 `Agent.stop(sessionID)`。
2. 关闭该会话的全部 SSE listener。
3. 保存会话最终状态。
4. 等待清理完成后退出进程。

## Config 指令

### `Config.load()`

读取配置文件并整体写入 `store.config`。这个动作只在服务启动时执行。

### `Config.get()`

返回 `store.config` 的深拷贝。API Key 和 `${ENV_NAME}` 占位符保持原值。

### `Config.update(partialConfig)`

把 `partialConfig` 递归合并到 `store.config`，调用 `Config.save()`，返回更新后的深拷贝。普通对象继续合并，数组和基础值整体替换。

### `Config.save()`

把完整 `store.config` 原子写入 `.agent/config.json`。先写临时文件，再替换正式文件，避免进程中断留下半份 JSON。

## Workspace 指令

### `Workspace.load()`

读取 `workspace.json` 并写入 `store.workspaces`。

### `Workspace.list()`

返回工作区及会话摘要的深拷贝。

### `Workspace.add(path)`

1. 确认 path 存在且是目录。
2. 创建 `{ id, path, sessions: [] }`。
3. 加入 `store.workspaces`。
4. 保存 `workspace.json`。
5. 返回新工作区。

### `Workspace.update(workspaceID, fields)`

找到工作区，把 fields 递归合并到该对象，保存并返回结果。普通对象继续合并，数组和基础值整体替换。

### `Workspace.remove(workspaceID)`

从 `store.workspaces` 移除工作区并保存。这个动作不删除工作区目录，也不删除已有会话文件。

## Session 指令

### `Session.get(sessionID)`

1. 如果 `store.sessions` 已缓存该会话，返回缓存。
2. 否则读取 `.agent/sessions/{sessionID}.json`。
3. 把未完成状态恢复为 `idle`。
4. 初始化 runtime 字段。
5. 放入 `store.sessions` 后返回。

### `Session.create(workspaceID)`

1. 确认工作区存在。
2. 创建新会话，标题为“新对话”，模型为 `store.config.defaultModel`，状态为 `idle`。
3. 初始化空消息、空 usage、空 rolledBack 和 runtime。
4. 放入 `store.sessions`。
5. 调用 `Session.save(sessionID)`。
6. 返回新会话。

### `Session.update(sessionID, fields)`

读取会话，把 fields 递归合并到会话，更新 `lastActiveAt`，保存并返回。普通对象继续合并，数组和基础值整体替换。

### `Session.delete(sessionID)`

1. 读取会话。
2. 如果会话不空闲，等待 `Agent.stop(sessionID)` 完成。
3. 关闭全部 listener。
4. 删除 session 文件并从 `store.sessions` 移除。
5. 从所属工作区的摘要缓存移除该会话并保存 `workspace.json`。
6. 返回被删除的 sessionID。

### `Session.save(sessionID)`

1. 从 session 中排除 runtime。
2. 原子写入 `.agent/sessions/{sessionID}.json`。
3. 用 session 的 `id`、`title`、`lastActiveAt` 更新所属工作区的摘要缓存。
4. 原子保存 `workspace.json`。

Session 模块是会话摘要的唯一所有者。常规同步集中在 `Session.save()`，删除只由 `Session.delete()` 处理，其他模块不得直接修改摘要。

### `Session.listen(sessionID, lastEventID)`

1. 读取会话并创建 SSE listener。
2. 把 listener 加入 `session.runtime.listeners`。
3. 如果提供 lastEventID，从事件缓冲补发缺失事件。
4. 无法补发时发送 `resync`。
5. 客户端断开后从 listeners 移除该连接。

## Agent 指令

### `Agent.send(sessionID, content)`

1. 读取会话；状态为 `running`、`waiting` 或 `retrying` 时返回 `SESSION_BUSY`。状态为 `error` 时允许开始新执行。
2. 创建用户 message 和 text block，二者各自使用会话内唯一 ID。
3. 把消息加入 `session.messages`，清空 `session.rolledBack`。
4. 把状态改为 `running` 并更新 `lastActiveAt`。
5. 保存会话，让 watcher 发布用户消息和状态变化。
6. 创建 runner，以后台任务启动 `Agent.run(sessionID)`。
7. 立即返回用户 message ID。

### `Agent.run(sessionID)`

Agent 循环只维护轮次和退出条件，不处理流片段或工具细节：

1. 把“连续未调用工具次数”初始化为 0。
2. 调用 `Turn.run(sessionID, reminder)` 完成一轮。
3. 本轮工具结果要求停止时，立即退出循环。
4. 本轮调用了工具时，把计数归零并开始下一轮。
5. 本轮没有调用工具时，把计数加一。
6. 第一次未调用工具时，直接开始下一轮。
7. 第二次未调用工具时，为下一轮设置临时工具提醒并继续。
8. 第三次未调用工具时，保留模型普通回复并退出循环。
9. 正常退出后清理 runtime，状态改为 `idle`，reason 为 `completed`，保存会话。

临时工具提醒只参与下一次 `Context.build()`，不加入 `session.messages`。工具调用成功出现后，连续计数归零。

### `Agent.stop(sessionID)`

1. 如果会话已经空闲，直接返回当前状态。
2. abort `session.runtime.runner`，同时中断模型请求和重试退避等待。
3. 把所有批准等待按 `reject` 结束。
4. 调用 `Tool.abortAll(sessionID)` 停止全部工具进程。
5. 清理 runner、waits 和 processes。
6. 把状态改为 `idle`，reason 为 `stopped`，保存会话。

stop 应可重复调用，重复调用不产生额外副作用。

## Turn 指令

### `Turn.run(sessionID, reminder)`

一轮模型交互按以下步骤执行：

1. 调用 `Context.build(sessionID, reminder)` 构建上下文。
2. 根据 `session.model` 找到已启用供应商和模型。
3. 在请求前解析 `apiKey` 中的 `${ENV_NAME}`，不修改 store 中的原值。
4. 创建空助手消息并加入 session。
5. 发起流式模型请求，交给 `Stream.consume()` 写内容块。
6. 请求成功后记录 usage、完成助手消息并保存。
7. 收集该消息中的全部 `tool_call` 块。
8. 没有工具调用时返回 `{ hasToolCalls: false }`。
9. 有工具调用时调用 `Tool.runAll()`，把全部结果加入一个 tool message 并保存。
10. 返回 `{ hasToolCalls: true, shouldStop }`。

### 无限重试

网络超时、限流和供应商 5xx 视为可重试错误：

1. 会话状态改为 `retrying`，watcher 发布 `error`，其中 `willRetry` 为 true。
2. 使用指数退避等待，等待时间可以设置合理的最大间隔，但**不设置重试次数上限**。
3. 等待结束后把状态改回 `running`，重试同一次模型请求。
4. runner 被 abort 时立即停止等待并结束本轮。

供应商 4xx、配置错误和响应格式错误视为不可重试错误。会话状态改为 `error`，reason 为 `failed`，循环结束。

## Stream 指令

### `Stream.consume(sessionID, messageID, stream)`

Stream 只负责把供应商流统一写成内容块：

- `text_delta`：没有当前 text block 时先创建，再追加 delta。
- `thinking_delta`：没有当前 thinking block 时先创建，再追加 delta。
- `tool_use_start`：结束当前文本或推理块，创建 tool_call block。
- `tool_input_delta`：把 JSON 片段追加到当前 tool_call block 的输入缓冲。
- `tool_use_end`：解析完整输入，把工具块标记为 pending。
- `usage`：更新本次请求的 usage。

每个新 block 立即获得会话内唯一 ID。delta 只修改内存并由 watcher 发布，不逐片写入会话文件。

## Tool 指令

### `Tool.runAll(sessionID, toolCalls)`

对同一轮的全部 tool call 同时调用 `Tool.run()`，再用 `Promise.all` 等待全部完成。所有工具一律并行，包括写入同一路径的文件工具；设计不增加路径互斥或执行顺序保证。

结果保持与 toolCalls 相同的顺序，以便稳定写入 tool message。

### `Tool.run(sessionID, toolCall)`

1. 从 `store.config.tools` 读取该工具的 permission。
2. `allow`：直接执行。
3. `deny`：生成拒绝结果，不启动工具。
4. `ask`：把工具块标记为 waiting，并调用 `Approval.wait()`。
5. 决定为 `once` 或 `always` 时执行；决定为 `reject` 时生成拒绝结果。
6. 返回 tool_result block。

### `Tool.execute(sessionID, toolCall)`

找到工具定义，记录进程引用，执行工具，最后无论成功失败都移除进程引用。工具异常转换为 `isError: true` 的结果块，不中断其他并行工具。

### `Tool.abortAll(sessionID)`

并行终止 `session.runtime.processes` 中的全部进程，等待退出后清空集合。

## Approval 指令

### `Approval.wait(sessionID, toolCallID)`

创建一个 30 分钟超时的 Promise，把其完成入口存入 `session.runtime.waits`。超时后按 `reject` 完成并移除等待对象。

至少存在一个等待时 session status 为 `waiting`；最后一个等待结束后恢复为 `running`。

### `Approval.once(sessionID, toolCallID)`

用 `once` 完成对应等待，不修改配置。

### `Approval.always(sessionID, toolCallID)`

把工具 permission 改为 `allow`，保存配置，再用 `always` 完成对应等待。

### `Approval.reject(sessionID, toolCallID)`

用 `reject` 完成对应等待，不修改配置。

路由根据 decision 直接调用上述三个具体动作，不使用一个方法在内部再次分派业务动作。

## History 指令

所有历史动作只允许在 session status 为 `idle` 或 `error` 时执行。

### `History.rollbackMessage(sessionID, messageID)`

1. 找到目标用户消息；非用户消息不能通过该动作撤回。
2. 把目标消息及之后全部消息从 `session.messages` 移除。
3. 写入 `session.rolledBack`，source 为 `message`。
4. 保存并返回完整会话。

### `History.rollbackBlock(sessionID, blockID)`

1. 找到包含目标 block 的消息。
2. 保存该消息回退前的完整原值。
3. 移除目标 block 以及该消息中后续所有 block。
4. 重新计算该消息的纯文本 content。
5. 移除该消息之后的全部消息。
6. 写入 `session.rolledBack`，source 为 `block`。
7. 保存并返回完整会话。

### `History.undo(sessionID)`

根据 `rolledBack.source` 恢复原消息或被移除消息，清空 rolledBack，保存并返回完整会话。

发送新消息会清空 rolledBack，因此只能撤销最近一次回退。

## Session Watcher

`watchers/session.js` 是会话反馈的唯一出口。业务指令在完成对应数据修改后调用 `SessionWatcher.publish(sessionID, event, data)`，由它负责：

1. 把明确的数据变化映射成 [接口.md](接口.md) 定义的事件。
2. 为事件分配递增 eventID。
3. 把事件加入最近 500 条环形缓冲。
4. 向当前全部 listener 发送事件。
5. listener 失败时关闭并移除连接。

事件名称必须来自 [接口.md](接口.md) 的固定事件表，不接受任意字符串。watcher 不做模型、工具、审批或历史业务判断。
