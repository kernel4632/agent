# 上下文压缩

## 问题

长任务会话可能跑几十上百轮工具调用，消息历史会超出模型的 token 上限。不处理的话，要么 API 直接报错，要么早期上下文被截断导致 Agent 遗忘关键信息。

## 核心原则

- 压缩只影响发送给 LLM 的内容，不修改前端显示的消息列表和持久化文件
- 前端始终展示完整消息历史，保留回退功能
- 系统提示词等常驻内容不参与压缩计算

## 两种压缩模式

### 模式 A：正常压缩（有余量时）

当消息历史接近阈值但未超出时，调用 LLM 生成中间部分的摘要。

### 模式 B：紧急裁剪（已超出时）

当上下文已经超出限制（比如未配置压缩专用模型、使用当前模型且刚好切换到小上下文的模型时），直接丢弃中间靠前的消息，逐条减少直到总量在上下文空间内。不调用 LLM。

## 触发时机

每次调用 LLM 前，估算当前消息历史的 token 总量（排除系统性常驻内容）：

- 未超过阈值 → 正常发送
- 超过阈值但未超出上限 → 模式 A（摘要压缩）
- 已超出上限 → 模式 B（紧急裁剪）

阈值 = 当前模型 maxTokens 的 80%（可在配置中调整）。

## 消息区域划分

```
┌──────────────────────────────────────────┐
│  头部保留区（最前面 N 条）                  │  ← 原样保留
│  包含：用户首条消息、初始需求上下文          │
├──────────────────────────────────────────┤
│  中间区域                                  │  ← 压缩/裁剪目标
│  包含：中间的工具调用、推理、结果            │
├──────────────────────────────────────────┤
│  尾部保留区（最近 N 条）                    │  ← 原样保留
│  包含：最近的对话轮次、当前工作上下文        │
└──────────────────────────────────────────┘
```

- 头部保留：默认前 4 条消息（用户原始需求 + Agent 首次回复）
- 尾部保留：默认后 10 条消息（最近的工作上下文）
- 中间区域：压缩或裁剪的目标

## 模式 A 流程（摘要压缩）

```
消息历史 token 超过阈值
        │
        ▼
┌─────────────────────────────────────────────────┐
│  1. 划分区域                                      │
│     ├── 头部保留区：前 4 条                        │
│     ├── 中间区域：第 5 条 ~ 倒数第 11 条           │
│     └── 尾部保留区：最后 10 条                     │
└──────────────────┬──────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────┐
│  2. 生成摘要                                      │
│     用 LLM 将中间区域总结为结构化摘要              │
└──────────────────┬──────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────┐
│  3. 组装发送给 LLM 的消息                         │
│     [ 头部保留 ] + [ 摘要消息 ] + [ 尾部保留 ]     │
└─────────────────────────────────────────────────┘
```

## 模式 B 流程（紧急裁剪）

```
上下文已超出模型上限（无法调用 LLM 生成摘要）
        │
        ▼
┌─────────────────────────────────────────────────┐
│  1. 保持头部和尾部保留区不变                       │
│  2. 从中间区域的靠前位置开始逐条移除消息           │
│  3. 每移除一条重新估算 token 总量                  │
│  4. 直到总量在模型上下文空间内                     │
└─────────────────────────────────────────────────┘
```

裁剪顺序：中间区域从前往后移除（越早的消息越可能过时）。

## 摘要消息格式

```javascript
{
  role: "system",
  content: `[上下文摘要 - 第5条至第32条消息的压缩]

## 已完成的操作
- 读取了 src/app.js，确认使用 Express 框架
- 将路由从 CommonJS 重构为 ES Module
- 修改了 package.json 添加 "type": "module"

## 关键决策
- 用户要求保留向后兼容性
- 选择逐文件迁移而非一次性重构

## 当前状态
- 已迁移 3/8 个路由文件
- 下一步：迁移 src/routes/auth.js`
}
```

## 摘要生成 Prompt

```
请将以下对话历史压缩为结构化摘要。保留：
1. 用户的原始需求和关键指示
2. 已执行的所有操作（文件读写、命令执行）及其结果
3. 重要的决策和原因
4. 当前任务进度和下一步计划

删除：工具返回的完整文件内容、重复的中间推理、已被后续操作覆盖的早期结果。

格式要求：使用 Markdown，分为"已完成的操作"、"关键决策"、"当前状态"三个部分。
```

## 摘要用哪个模型

- 可在配置中指定压缩专用模型（便宜/快速模型）
- 未配置时使用当前激活模型
- 模式 B（紧急裁剪）不调用任何模型

## 系统性常驻内容

以下内容不参与压缩计算，始终原样保留在发送给 LLM 的请求中：

- system prompt（系统提示词）
- 工具定义列表（tools schema）

token 估算时先扣除这些常驻内容的占用，剩余空间分配给消息历史。

## Token 估算

使用简单的字符数估算（不引入 tiktoken 等重依赖）：

- 英文：1 token ≈ 4 字符
- 中文：1 token ≈ 1.5 字符
- 混合内容取保守估算

后续如需精确计算，可选装 tiktoken。

## 与前端/存档点的关系

| 层面 | 行为 |
|------|------|
| 发送给 LLM | 使用压缩后的消息（头部 + 摘要 + 尾部） |
| 前端显示 | 始终展示完整消息历史，不受压缩影响 |
| 持久化文件 | 始终保存完整消息历史 |
| 存档点回滚 | 基于完整历史操作，与压缩无关 |

压缩是一个纯运行时行为，只存在于"构造 LLM 请求"这一刻。
