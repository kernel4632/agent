# 上下文压缩

## 问题

长任务会话可能跑几十上百轮工具调用，消息历史会超出模型的 token 上限。不处理的话，要么 API 直接报错，要么早期上下文被截断导致 Agent 遗忘关键信息。

## 核心原则

- 压缩只影响发送给 LLM 的内容，不修改前端显示的消息列表和持久化文件
- 前端始终展示完整消息历史，保留回退功能
- system prompt 和 tools schema 不参与压缩（常驻内容）

## 压缩逻辑

将完整消息历史压缩为三段结构发送给 LLM：

```
发送给 LLM 的内容：

┌──────────────────────────────────────────┐
│  头部保留区（最前面几条原始消息）           │
├──────────────────────────────────────────┤
│  摘要（role: assistant）                  │  ← 中间所有消息压缩成这一条
├──────────────────────────────────────────┤
│  尾部保留区（最近几条原始消息）            │
└──────────────────────────────────────────┘
```

**全部消息都参与压缩范围**，头部和尾部保留只是"原样保留的条数"，它们之间的所有消息压缩为一条 assistant 消息放在中间。

## 两种压缩模式

### 模式 A：正常压缩（有余量，能调用 LLM 生成摘要）

当消息历史接近阈值但还能调用 LLM 时：

1. 取头部保留区（前 4 条）
2. 取尾部保留区（后 10 条）
3. 将中间所有消息发给 LLM 生成结构化摘要
4. 摘要作为一条 `{ role: "assistant" }` 消息插在头部和尾部之间
5. 组装后发送：头部 + 摘要 + 尾部

### 模式 B：紧急裁剪（已超出，无法调用 LLM）

当上下文已经超出限制（比如切换到小上下文模型），无法调用 LLM 生成摘要时：

1. 保持头部和尾部保留区不变
2. 从中间区域靠前的位置开始逐条移除消息
3. 每移除一条重新估算 token 总量
4. 直到总量在模型上下文空间内

裁剪顺序：从中间靠前往后移除（越早的越可能过时）。

## 触发时机

每次调用 LLM 前，估算当前消息历史的 token 总量（排除 system prompt 和 tools schema）：

- 未超过阈值 → 正常发送完整历史
- 超过阈值但未超出上限 → 模式 A（摘要压缩）
- 已超出上限 → 模式 B（紧急裁剪）

阈值 = 当前模型 maxTokens 的 80%（可在配置中调整）。

## 摘要消息格式

摘要以 assistant 角色插入，因为它是对之前 Agent 行为的总结：

```javascript
{
  role: "assistant",
  content: `[以下是之前对话的压缩摘要]

## 已完成的操作
- 读取了 src/app.js，确认使用 Express 框架
- 将路由从 CommonJS 重构为 ES Module
- 修改了 package.json 添加 "type": "module"
- 运行 npm test 确认无报错

## 关键决策
- 用户要求保留向后兼容性
- 选择逐文件迁移而非一次性重构

## 当前状态
- 已迁移 3/8 个路由文件
- 下一步：迁移 src/routes/auth.js`
}
```

## 摘要生成 Prompt

```
请将以下对话历史压缩为结构化摘要。保留：
1. 用户的原始需求和关键指示
2. 已执行的所有操作（文件读写、命令执行）及其结果
3. 重要的决策和原因
4. 当前任务进度和下一步计划

删除：工具返回的完整文件内容、重复的中间推理、已被后续操作覆盖的早期结果。

格式要求：使用 Markdown，分为"已完成的操作"、"关键决策"、"当前状态"三个部分。
```

## 摘要用哪个模型

- 可在配置中指定压缩专用模型（便宜/快速模型）
- 未配置时使用当前激活模型
- 模式 B（紧急裁剪）不调用任何模型

## 系统性常驻内容（不参与压缩）

以下内容始终原样发送，不计入压缩范围：

- system prompt（系统提示词）
- 工具定义列表（tools schema）

token 估算时先扣除这些常驻内容的占用，剩余空间分配给消息历史。

## Token 估算

使用简单的字符数估算（不引入 tiktoken 等重依赖）：

- 英文：1 token ≈ 4 字符
- 中文：1 token ≈ 1.5 字符
- 混合内容取保守估算

后续如需精确计算，可选装 tiktoken。

## 与前端/存档点的关系

| 层面 | 行为 |
|------|------|
| 发送给 LLM | 头部原始消息 + 摘要(assistant) + 尾部原始消息 |
| 前端显示 | 始终展示完整消息历史，不受压缩影响 |
| 持久化文件 | 始终保存完整消息历史 |
| 存档点回滚 | 基于完整历史操作，与压缩无关 |

压缩是一个纯运行时行为，只存在于"构造 LLM 请求"这一刻。

## 示例

完整消息历史有 50 条消息，头部保留 4 条，尾部保留 10 条：

```
完整历史（前端显示 & 持久化）：
[msg1] [msg2] [msg3] [msg4] [msg5] ... [msg40] [msg41] ... [msg50]

发送给 LLM 的：
[msg1] [msg2] [msg3] [msg4] [摘要：msg5~msg40的压缩] [msg41] ... [msg50]
```
